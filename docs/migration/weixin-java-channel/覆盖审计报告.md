**覆盖率解读（为什么 line% 与 fn% 差异大）**：

1. **bean 密度极高、结构体自身贡献低**：台账 618 对象中约 503 个文件是 bean（50+ 子域，含
   消息子系统 bean/message/* 50 类）。serde 派生的结构体字段声明行计入 llvm-cov 分母，
   测试多经「服务请求/响应解析」路径触达（from_json/Deserialize 宏展开），结构体自身声明行与
   未走到的 `#[serde]` 分支不被计数——bean 层把 line 分母拉大；同时 `fn%` 低是因为
   大量结构体方法（getter 等价语义、私有构造）与 25 个子服务 208 个方法中未被代表性用例
   触达的方法计入函数分母（`fn 27.65%` vs `line 52.36%` 的剪刀差即源于此）。
2. **服务层覆盖集中**：45 个集成测试覆盖 11 个服务（shop 组）的请求/响应契约 + 门面执行引擎；
   其余 14 个子服务由内嵌单元 34 个覆盖（每服务 2–5 个代表性用例，URL/请求体/响应解析），
   服务内全分支（参数校验、错误分支、重载变体）未全覆盖。
3. **未覆盖热点清单**（静态触达分析，见下表）：
   - **加解密路径（Wave 5.1 已补齐）**：`util/wx_ch_crypt_utils.rs`（消息加解密 + 用户会话
     数据解密）官方向量/往返单元已覆盖主路径（AES-128-CBC + PKCS7、消息签名往返、错误签名
     拒绝）；错误 Base64/非法密钥长度等分支未逐一覆盖；
   - **消息路由热点**：21 个 message 测试覆盖 router/rule 主路径，但 `bean/message/*` 50 类中
     大量消息 bean（fund/after/coupon/vip/supplier/store/voucher 事件）仅少数被
     `json_unpack_*`/`xml_unpack_*` 单元触达，其余从 JSON 到结构体的反序列化分支未逐一覆盖
     （典型如 `OrderExtMessage`/`SessionMessage`/`ComplaintMessage` 嵌套结构）；
   - **executor 与 util adaptor 无独立文件**（台账 DEPENDENCY_REUSED 6 + PLATFORM_NA 9）：
     上传/下载执行语义内化于门面默认实现与 wx-rust-common util::http，线格式/解码语义内化于
     serde/quick-xml 与 `post_as` 解码辅助，无独立覆盖单元；
   - **配置层**：`config/impl/wx_channel_default_config_impl.rs` 的过期判定/锁分支仅经
     门面缓存测试间接触达。
