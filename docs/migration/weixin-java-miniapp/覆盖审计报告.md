**覆盖率解读（为什么 line% 偏低）**：

1. **bean 密度高、结构体自身贡献低**：miniapp 611 行台账中约 472 个是 bean（31 子域）。
   serde 派生的结构体行（字段声明 + 派生宏展开）在 llvm-cov 中计入可执行行，
   但测试多经“服务请求/响应解析”路径触达（from_json/Deserialize 宏展开），
   结构体自身声明行与未走到的 `#[serde]` 分支不被计数——bean 层把 line 分母拉大，
   这是 line% 35.49% 的主要结构性原因，与 mp/common 同因（common 27.00% 更低）。
2. **服务层覆盖集中**：45 个服务 impl 被测试直接引用（55 个服务对象），路径/payload/
   响应解析集中在 g1–g4 六组 MockServer 测试；每服务仅 1–3 个代表性用例
   （75 个集成测试覆盖 55 个服务对象中的 45 个），服务内全分支（参数校验、
   错误分支、重载变体）未全覆盖。
3. **未覆盖热点清单**（静态触达分析，见下表）：
   - **10 个服务 impl 零测试触达**：employee_relation、express_delivery_return、
     live_member、order_management、shop_audit、shop_coupon、shop_delivery、
     shop_img、shop_pay、shop_sharer（对应 Java 侧也恰好无对应测试文件或测试未镜像）
   - **util/json adaptor 与 executor 无独立文件**（台账 DEPENDENCY_REUSED 16 项）：
     线格式内化于 bean serde 与服务实现，无独立覆盖单元
   - **bean 子域中低触达**：shop/response、promoter/response、delivery 等响应 bean
     的 from_json 分支经服务测试覆盖，但请求侧可选字段组合（Option 分支）覆盖有限
